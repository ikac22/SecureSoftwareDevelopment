# CWE-943 — vulnerable application

## Goal

Demonstrate the NoSQL injection described in issue #20 against the unmitigated service-history search implementation.

The experiment uses one combined request that attempts both effects described in the thesis:

1. replace the implicit ownership condition with a MongoDB operator supplied through `filters.customerId`;
2. extend the MongoDB projection through the client-controlled `view` object so internal fields are returned.

## Entry point

`POST /api/my/service-history/search`

The experiment authenticates the request as customer `id = 1` and sends:

```json
{
  "filters": {
    "customerId": {
      "$ne": 1
    }
  },
  "view": {
    "customerId": 1,
    "pricingPolicy": 1
  }
}
```

## Source-to-sink flow

The vulnerable flow is:

```text
HTTP JSON filters/view
        |
        v
ServiceHistoryController.ServiceHistorySearch
(Map<String, Object>)
        |
        v
ServiceHistoryService.search(...)
        |
        v
ServiceHistorySearchRepository.search(...)
        |
        +--> new Document(effectiveFilters)
        |        |
        |        +--> putIfAbsent("customerId", authenticatedCustomerId)
        |
        +--> baseProjection().putAll(effectiveView)
        |
        v
MongoDB aggregate([$match, $project, $sort])
```

The ownership condition is vulnerable because `putIfAbsent` does not replace a client-provided `customerId`. Therefore the supplied object `{"$ne": 1}` reaches MongoDB as an operator expression instead of customer data.

The response projection is independently extensible because all entries from the request `view` map are copied into `$project`.

## Automated reproduction

Run from the repository root:

```bash
bash attacks/cwe-943/run-attack.sh vulnerable
```

The harness executes `Cwe943ExperimentTests` against the real Spring service/repository path and embedded MongoDB used by the integration tests.

It writes the following evidence files:

```text

```

## PASS criteria

The vulnerable experiment passes only when all of the following are observed in the actual HTTP response generated through `MockMvc`:

- HTTP status is `200`;
- at least one completed service belonging to a customer other than `id = 1` is returned;
- `customerId` is present in the returned data;
- `pricingPolicy` is present in the returned data.

The harness fails the Maven test if any of these conditions is missing.

## Expected deterministic fixture

The repository seed contains completed service `serviceId = 4` for `customerId = 2`, while the experiment is authenticated as customer `id = 1`. The same record also contains `pricingPolicy` metadata. This makes the observable effect deterministic without modifying application data during the attack.

## Evidence

The evidence directory is generated by the automated harness. `request.json` records the exact payload, `response.json` records the actual application response, and `result.txt` records the boolean PASS observations used by the test. `maven-output.txt` contains the complete test invocation output.

No production code is changed before collecting the vulnerable evidence.
