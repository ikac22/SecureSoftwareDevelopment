# CWE-943 — vulnerable application

## Goal

Demonstrate the NoSQL injection described in issue #20 against the unmitigated service-history search implementation.

The experiment uses one combined request that attempts both effects described in the thesis:

1. replace the implicit ownership condition with a MongoDB operator supplied through `filters.customerId`;
2. extend the MongoDB projection through the client-controlled `view` object so internal fields are returned.

## Entry point

`POST /api/my/service-history/search`

The experiment authenticates the request as customer `id = 1` and sends:

```json
{
  "filters": {
    "customerId": {
      "$ne": 1
    }
  },
  "view": {
    "customerId": 1,
    "pricingPolicy": 1
  }
}
```

## Source-to-sink flow

The vulnerable flow is:

```text
HTTP JSON filters/view
        |
        v
ServiceHistoryController.ServiceHistorySearch
(Map<String, Object>)
        |
        v
ServiceHistoryService.search(...)
        |
        v
ServiceHistorySearchRepository.search(...)
        |
        +--> new Document(effectiveFilters)
        |        |
        |        +--> putIfAbsent("customerId", authenticatedCustomerId)
        |
        +--> baseProjection().putAll(effectiveView)
        |
        v
MongoDB aggregate([$match, $project, $sort])
```

The ownership condition is vulnerable because `putIfAbsent` does not replace a client-provided `customerId`. Therefore the supplied object `{"$ne": 1}` reaches MongoDB as an operator expression instead of customer data.

The response projection is independently extensible because all entries from the request `view` map are copied into `$project`.

## Versioned experiment snapshots

The attack test is intentionally shared by both application states. The two states are preserved as immutable Git tags:

- `cwe-943-vulnerable` — the last commit that contains the attack harness and evidence while production code is still vulnerable;
- `cwe-943-mitigated` — the final mitigated snapshot used for the repeated attack.

For this experiment, the vulnerable snapshot is commit `183e109e74e6bddd9262ca35d94d2f6988fb3502`, immediately before the mitigation commits begin.

After the mitigated implementation is finalized, create and optionally push the tags from the experiment branch:

```bash
bash attacks/cwe-943/tag-snapshots.sh --push
```

The helper refuses to move an existing snapshot tag to another commit. If a tag already exists with a different target, the experiment stops instead of silently changing historical evidence.

## Automated reproduction

Run both snapshots from the repository root:

```bash
bash attacks/cwe-943/run-attack.sh
```

The runner resolves the two tags and checks each one out into a temporary detached Git worktree. It then executes the same `Cwe943ExperimentTests` class twice:

- against `cwe-943-vulnerable` with `-Dcwe943.phase=vulnerable`, where the attack is expected to succeed;
- against `cwe-943-mitigated` with `-Dcwe943.phase=mitigated`, where the same attack is expected not to produce the vulnerable effect and the positive control must still work.

A single phase can still be executed explicitly:

```bash
bash attacks/cwe-943/run-attack.sh vulnerable
bash attacks/cwe-943/run-attack.sh mitigated
```

Using temporary worktrees keeps the caller's current checkout unchanged while still running the test against the exact tagged source trees.

The harness writes evidence to:

```text
attacks/cwe-943/evidence/
├── vulnerable/
│   ├── request.json
│   ├── response.json
│   ├── result.txt
│   └── maven-output.txt
└── mitigated/
    ├── request.json
    ├── response.json
    ├── result.txt
    └── maven-output.txt
```

## PASS criteria

The vulnerable experiment passes only when all of the following are observed in the actual HTTP response generated through `MockMvc`:

- HTTP status is `200`;
- at least one completed service belonging to a customer other than `id = 1` is returned;
- `customerId` is present in the returned data;
- `pricingPolicy` is present in the returned data.

The mitigated execution uses the same attack request and passes only when the foreign service is not returned, the client cannot expose `customerId` or `pricingPolicy`, and the legitimate service-history search still succeeds.

## Expected deterministic fixture

The repository seed contains completed service `serviceId = 4` for `customerId = 2`, while the experiment is authenticated as customer `id = 1`. The same record also contains `pricingPolicy` metadata. This makes the observable effect deterministic without modifying application data during the attack.

## Evidence

The evidence directory is generated by the automated harness. `request.json` records the exact payload, `response.json` records the actual application response, and `result.txt` records the boolean PASS observations used by the test. `maven-output.txt` contains the complete test invocation output.

The important invariant is that the same test and same attack request are evaluated against two immutable application snapshots, so the before/after comparison is tied to concrete Git commits rather than to whichever code happens to be checked out when the experiment is run.
